## What this is

TalkMate is an AI language-practice web app (a Talkpal-style clone; the UI even says "in this clone"). A learner picks a target language and level, then practices in ten "modes": Chat, Call (voice), Sentence, Word, Dialogue, Roleplays, Characters, Debates, Photo and Flashcards. Practice earns XP, levels, streaks and achievements, and an LLM writes daily feedback.

**Every mode is page-based: Home pushes a route (`/chat`, `/call`, `/word`, ...) and no mode opens as a modal any more.** Chat is the only mode the UI leaves free; the other nine need Premium (UI-only, see gotcha 1). The old `ChatPanel` is deleted, and `GeneratePanel` and `PhotoPanel` are unreachable dead code. Dialogue (`/dialogue`, 21 topics): a picture grid of topics, a topic intro page with Start, then a practice screen where a partner speaks a line and the learner reads their answer aloud for a 1-5 rating (backend `src/dialogue`: catalog, prompts, in-memory script cache, `GET /dialogue/topics`, `POST /dialogue/session`, `POST /dialogue/complete`; progress in `DialogueProgress` (best score, attempts, passed; check badge on the grid); pronunciation reuses `/sentence/evaluate`; the old `GeneratePanel` dialogue type is now legacy). Sentence (`/sentence`, 10 units x 3 skills): the AI writes 5 sentences for a skill, the learner hears them, reads them aloud, and gets a 1-5 pronunciation rating. Word (`/word`, 10 units x 12 stars): each star is one word with a photo, then 3 sentences made from the word, rated the same way, and an unfinished lesson can be resumed. Flashcards (`/flashcards`, 18 topics x 15 cards): a topic grid, then a full-screen deck where the learner sees a photo, the word, its sound and an example sentence and marks each card "Learning" or "I know it"; marked cards feed a Daily review. Roleplays (`/roleplay`, 24 scenarios): a picture grid with a category pill, an intro page (Scenario, Your tasks, Start), then a chat where the AI plays the other person and a side panel reviews each learner message (see "Roleplay Mode"). See "Sentence Mode", "Word Mode" and "Flashcards Mode" below.

**Characters is page-based too** (`/characters`, 30 characters): a portrait grid, a character intro page with Start, then a full-screen chat where the character speaks the learner's language and a right-hand panel reviews each learner message (backend `src/characters`; conversations are saved per user, character and language). See "Characters Mode" below.

**Chat is page-based** (`/chat`, one full-screen page, free for everyone): a free conversation with one of four AI tutors (Emma, Kai, Nina, Niko), a right-hand panel that reviews each learner message, a suggestion bar of three tappable replies, saved chats and a Chat history (backend `src/chat`; see "Chat Mode" below).

**Call is page-based too** (`/call`, one full-screen page): an audio-only phone call with the same four tutors (default Kai), a right-hand panel that reviews what the learner said, an "Advanced feedback" button, a saved open call and a Call history (backend `src/call`; see "Call Mode" below).

**Debates are page-based too** (`/debate`, 24 topics): a topic grid, an intro page with "Argue for" / "Argue against", then a chat where the teacher Kai takes the other side and a right-hand panel reviews each learner message (backend `src/debate`; see "Debate Mode" below).

**Photo is page-based too** (`/photo`, 2 units x 8 stars built in; the grid shows 6 stars per row, so a unit of 12 is two full rows): a star grid, then a full-screen page with a picture and a text/mic box where the AI judges the learner's description (see "Photo Mode" below). The old `PhotoPanel` upload modal is now legacy.

**Explore is a dashboard tab too** (frontend only, no backend or DB change): today's picks for every mode, chosen from the lists the mode pages already load. See "Explore" below.

**Courses and Learn are dashboard tabs** (frontend only, no backend or DB change): Courses is a grid of 32 courses, and picking one makes it the selected course and opens Learn, a learning path of units whose three exercises open Word, Sentence and Dialogue Mode. See "Courses and Learn" below.

**Account is a dashboard tab**, not a modal: Profile, Personalization, Settings (translation language, target language, level), demo Subscriptions, Refer-a-friend and Support. See "Account" below. There is no real billing.

**Admin panel** (`/admin`, only for emails listed in `ADMIN_EMAILS`): a compact table of every element of the eight content modes (Sentence, Word, Flashcards, Dialogue, Debate, Characters, Roleplay, Photo; built-in and added together) with search, a group filter and an "Added by admin" filter, plus a form and a JSON import to add new elements without touching code. Added elements go live for every learner at once. **Every element, built-in or added, can be edited or deleted**; a changed built-in element can be reset to its original and a deleted one restored. All of it lives in the database table `ContentItem` (see "Content (`src/content`)"). See "Admin (`src/admin`)" and "Admin panel (`app/admin`)" below. Chat and Call have no catalog (only the four tutors), so they are not in the panel.

Monorepo with two independent apps, **no root `package.json`**. Run every npm command inside `backend/` or `frontend/`.

The backend logs OpenRouter's reason for each failure (`<model> -> 429 <reason>`).

## Backend in detail

### Bootstrap (`main.ts`)
- `bodyParser: false`, then `json({ limit: '6mb' })`. Needed for base64 photos (the DTO allows up to 5,000,000 chars).
- `trust proxy` = 1 (so throttling sees the real client IP behind one proxy).
- CORS allows only the origins in `FRONTEND_URL`.
- CORS is enabled **before** the static files, so `/media/*` pictures also carry the CORS header (Photo Mode shrinks a photo on a canvas, which needs it for pictures uploaded in the Admin panel; see gotcha 62).
- Static files: `app.useStaticAssets(MEDIA_DIR, { prefix: '/media/', maxAge: '7d' })` (`MEDIA_DIR` imported from `word/word.images.ts`). It must serve the same folder the photo services write to (see gotcha 54).
- Global `ValidationPipe({ whitelist: true, transform: true })`: unknown properties are silently stripped, so a new request field **must** be added to the DTO or it will vanish.

### Rate limiting
Global `ThrottlerGuard`: 20 requests / 60 s per client. Overrides: `AuthController` 10 / 60 s (`forgot-password` and `resend-verification` 3 / 60 s, because each can send an email); `/sentence/evaluate` 40; the chat-style controllers (`chat`, `call`, `debate`, `characters`, `roleplay`) 40 (every turn is a reply plus a review); `progress` 120 (every page loads it and the timer reports every 30 s); `PATCH /flashcards/mark` 120; `POST /account/password` 5; `POST /account/support` 3. Word, Photo, Dialogue, the rest of Flashcards and Account and `/ai/*` use the default 20. This protects the free OpenRouter quota and password guessing.

### Auth (`src/auth`)
- `POST /auth/register`: email lowercased/trimmed, 409 if a **verified** account has it, bcryptjs cost 10, requires `firstName` and `lastName` (non-blank, max 60 each, trimmed; saved to `User.name`, which is the first name, and `User.lastName`), checks the domain can receive mail (`assertDeliverable`: MX lookup, falls back to an address record, rejects a null MX such as example.com; a DNS timeout is not held against the user), creates `User` (`emailVerified = false`) and an empty `Progress` in one nested create, emails a 6-digit code and returns `{ verify: true, email }` with **no token**. An earlier unverified sign-up for the same address is taken over (names and password replaced) instead of answering 409, so a typo never locks an address. An optional `referralCode` (4-12 letters/digits, upper-cased before lookup) links the new user to the inviter through `User.referredById`; an unknown code is silently ignored so a typo never blocks sign-up.
- `POST /auth/login`: same error ("Invalid email or password.") for unknown email and wrong password. Keep it that way to avoid account enumeration. After a correct password, an account whose email is not verified gets 403 `{ message, code: 'EMAIL_NOT_VERIFIED' }` and a fresh code is emailed (the 60 s cooldown applies).
- `POST /auth/google` `{ credential, referralCode?, remember? }`: the credential is a Google Identity Services ID token. The backend asks `https://oauth2.googleapis.com/tokeninfo` to validate it (no `google-auth-library`, so no new dependency), then requires `aud === GOOGLE_CLIENT_ID`, a Google `iss` and a verified email. Lookup order: `User.googleId`, then the same email (links the Google id to the existing account), else it creates a user (name from Google, empty `Progress`, optional referral, `emailVerified = true`). Linking Google to an existing **unverified** password account marks it verified and clears its password, so whoever pre-registered the address cannot keep access. Accounts made this way have `passwordHash = null`, so `/auth/login` rejects them with the usual generic message and `PATCH` change-password answers 400 pointing to "Forgot your password?".
- `POST /auth/forgot-password` `{ email }` (throttled 3 / 60 s): always returns `{ ok: true }` (no account enumeration). For a real user it deletes older `PasswordResetToken` rows, stores the sha256 of a random 32-byte token (1 hour expiry) and emails `<FRONTEND_URL>/reset-password?token=...` through `MailService` (Gmail SMTP via nodemailer when `GMAIL_USER` and `GMAIL_APP_PASSWORD` are set, else the Resend HTTP API, else a log line). A send failure is logged but still answers ok.
- `POST /auth/reset-password` `{ token, password }`: 400 if the token is unknown or expired; otherwise sets the new bcrypt hash and deletes all of the user's reset tokens (single use). This also lets a Google-only user set a first password, and it marks the email verified (the link proved ownership). Existing JWTs are not revoked (stateless).
- `POST /auth/verify-email` `{ email, code, remember? }`: the code is stored as `sha256(userId:code)` in `EmailVerification` (one row per user, 15 minute expiry). Each call counts a try first; after 5 wrong tries the row is deleted and a new code is needed. A wrong, expired or missing code gets the same 400 message. Success sets `User.emailVerified = true`, deletes the row and returns `{ token, user }`.
- `POST /auth/resend-verification` `{ email }` (throttled 3 / 60 s): always `{ ok: true }` (no enumeration); sends a new code only for an unverified password account, and not within 60 s of the last code. If the mail cannot be sent, the code row is deleted so the cooldown does not block a retry, and register answers 503.
- "Remember this device": `remember` on login/google/verify-email (register no longer signs in) picks a 30-day JWT, otherwise 1 day. The frontend stores the token in `localStorage` when remembered and in `sessionStorage` otherwise (`getToken` checks both, `clearToken` clears both).
- JWT: `JwtModule.registerAsync({ global: true })`, secret from `JWT_SECRET`, default 7-day expiry overridden per login by `remember`, payload `{ sub, email }`. No refresh tokens.
- `AuthGuard` parses `Authorization: Bearer <token>` and sets `req.user = { id, email }`. Controllers read `req.user.id`.
- Frontend pages: `/login` (an animated robot illustration built from layers in `public/login/robot/`, shown beside the card on large screens; Google button via Google Identity Services, remember checkbox), `/forgot-password`, `/reset-password?token=` (both use `AuthShell`).
- DTOs: register email max 254, password 8..72 with at least one lowercase letter, one uppercase letter and one number (`PASSWORD_RULE` in `auth/password.rule.ts`, shared with reset-password and `POST /account/password`; bcrypt ignores bytes past 72), `firstName` and `lastName` both required, max 60 each and must contain a non-space character (the old optional `name` field is gone, and `whitelist: true` strips it if an old client still sends it). Login password max 72 and no strength rule, so passwords made before the rule still work. `VerifyEmailDto` = email + `code` (exactly 6 digits) + `remember?`; `ResendVerificationDto` = email.

### Progress (`src/progress`)
Constants: `STUDY_SECONDS = 180`, `XP_PER_LEVEL = 50`. Dates in this file are **UTC** (`ymd = toISOString().slice(0,10)`).

- `snapshot(userId)` is what almost every endpoint returns: `{ email, name, avatar, xp, streak, longest, messages, premium, language, nativeLanguage, level, today: string[] }`. `name` is the first and last name joined (null when neither is set) and `avatar` is the profile picture data URL or null. `today` is the user's last 30 `PracticeEntry` texts for the UTC day, oldest first. If `lastDay` is more than 1 day before UTC today, `streak` is reported as 0 without writing to the DB.
- `snapshot()` first calls `syncPremium`, one extra query on every endpoint that returns a snapshot (see Account).
- `practice(text)`: in one transaction, `xp += 10`, `messages += 1`, insert `PracticeEntry` (text truncated to 1000). Returns a snapshot.
- `addTime(seconds, day)`: `day` is the **browser's local date**. Rejected (400 "Invalid day") if more than 1 day away from UTC today. Upserts `PracticeDay` (increments seconds). Only when this call makes the day's total cross 180 seconds does the streak change: gap = days between `lastDay` and `day`; if `lastDay` is null or gap > 0, `streak = gap === 1 ? streak + 1 : 1`, `longest = max(...)`, `lastDay = day`.
- `stats()`: `{ totalSeconds, studiedDays (days >= 180s), activeDays (days > 0s), days: last 400 PracticeDay rows oldest-first, achievements }`.
- `settings(dto)`: updates `language` and `nativeLanguage` (any string up to 40 chars, not validated against the frontend list) and `level` (Beginner | Intermediate | Advanced). `ProgressModule` exports `ProgressService` because Sentence Mode calls `practice()`.
- `unlockPremium()`: demo only. It now calls `startSubscription` (account module), which creates or restarts a 1-month **demo subscription**, sets `premium = true`, and pays out a pending referral reward. It still works for any logged-in user.
- `ensure(userId)` upserts a `Progress` row defensively before every operation.
- Achievements are code, not data: the `ACHIEVEMENTS` array (ids `first_step`, `warm_up`, `on_a_roll`, `week`, `chatterbox`, `hour`, `level5`) is evaluated on each `stats()` call against facts (messages, longest streak, total seconds, studied days, level). Nothing is persisted per achievement.

### AI (`src/ai`)
All routes are behind `AuthGuard`.

- `POST /ai/chat` (**legacy: nothing in the frontend calls it any more**; Chat, Call, Debate, Characters and Roleplays each have their own module) `{ mode, messages[1..30], context?, targetLanguage?, nativeLanguage?, level? }` -> `{ reply }`. System prompt from `chatSystem(mode, learner, context)` is prepended server-side; clients may only send `user` / `assistant` roles (content max 2000). Temperature 0.8; max tokens 200 for `call`, 450 otherwise.
- `POST /ai/generate` `{ type, topic (max 120), count? (3..12), ...learner }` -> parsed JSON. Defaults: 8 items for flashcards, 6 otherwise; dialogue uses `max(count, 6)` lines. Temperature 0.6, max tokens 1400. Up to 2 attempts; the model output is stripped of code fences, the outermost `{...}` is extracted and `JSON.parse`d; both failing returns 502 "unreadable answer". Response shapes:
  - sentence: `{ items: [{ sentence, translation, note }] }`
  - word: `{ items: [{ word, translation, example, exampleTranslation }] }`
  - dialogue: `{ title, lines: [{ speaker: "A"|"B", text, translation }] }`
  - flashcards: `{ items: [{ front, back, hint }] }`
- `POST /ai/photo` `{ image (data:image/png|jpeg|webp;base64,..., max 5M chars), description? (max 1500) }` -> `{ feedback }`. Sends an OpenAI-style multimodal message (`image_url`). With a description the model grades it (Accuracy / Corrections / Better version / New words); without one it writes a sample description plus 5 words. Whether `openrouter/free` routes to a vision-capable model is not guaranteed; pin a vision model via `OPENROUTER_MODEL` if photos fail.
- `POST /ai/feedback` `{ texts[1..40] (each max 1000), ...learner }` -> `{ feedback }`. Writes strengths, up to 3 mistakes with corrections, one thing to practice tomorrow, under 150 words, in the learner's native language. Temperature 0.5, 500 tokens.
- `learner()` fallback defaults in `ai.service.ts`: target `Bengali`, native `English`, level `Beginner`. Every page sends the learner's saved `nativeLanguage` (the "Choose translation language" setting in Account > Settings) with every call, so corrections, translations and feedback are written in it. `LearnerDto` in `ai/dto.ts` is exported and reused by the Sentence DTOs.
- `prompts.ts` is the single place for tutor behavior:
  - chat: **legacy** `/ai/chat` mode (friendly teacher, 2-4 short sentences, adds a `Correction:` line). The live Chat Mode prompts are in `src/chat/chat.prompts.ts`.
  - call: **legacy** `/ai/chat` mode (1-2 short sentences, no emojis, markdown or lists because the reply is read aloud). Home now opens the page-based Call Mode, which has its own prompts in `src/call/call.prompts.ts`.
  - roleplay: plays the other party in a scenario (default restaurant), adds `(Tip: ...)`. **Legacy**: Home now opens the page-based Roleplay Mode, which has its own prompts in `src/roleplay`.
  - characters: no longer a `/ai/chat` mode. Its prompts live in `src/characters/characters.prompts.ts` (see Characters Mode).
  - debate: **legacy** `/ai/chat` mode. The live Debate Mode prompts are in `src/debate/debate.prompts.ts`.
  - generate prompts demand JSON only and embed the schemas above. Changing a schema means updating the prompt, `GeneratePanel` rendering and the response handling together.
- `OpenRouterService.complete()`: POST `https://openrouter.ai/api/v1/chat/completions` with `Authorization`, `X-Title: TalkMate`, 45 s timeout. Message content is text or `image_url` parts. For each model (primary, then fallbacks) up to 2 attempts: 200 with empty content moves to the next model; 401/402/403 throws 502 immediately ("Check your API key"); on other failures it reads OpenRouter's error text (`errorDetail`) and logs it. A 429 whose text mentions a daily limit throws 502 at once with a message saying today's free requests are used up (the quota is account-wide, so retrying or switching model cannot help). Other 429s and 5xx sleep 700 ms x attempt and retry; other statuses move on. Everything exhausted returns 502 "The free AI models are busy or rate limited." The service is exported from `AiModule` so Sentence Mode can use it.

### Sentence Mode (`src/sentence`)
All routes are behind `AuthGuard`. Nothing here checks `premium` (see gotcha 1).

- **Catalog** (`sentence.catalog.ts`): `SENTENCE_UNITS` = 10 units x 3 skills (`TOTAL_SKILLS` = 30). Skill ids are URL slugs (`basic-greetings`) and are the keys stored in `SentenceProgress`, so never rename one that users have progress on. Each skill has `title`, `description`, `emoji`. `findSkill(id)` looks one up.
- `GET /sentence/units` -> `{ percent, passed, total, units: [{ number, title, skills: [{ id, title, description, emoji, passed, bestScore, attempts }] }] }`. `percent` = passed skills / 30.
- `POST /sentence/session` `{ skillId, targetLanguage?, nativeLanguage?, level? }` -> `{ skillId, title, items: [{ sentence, translation, note }] }`. The prompt (`sessionSystem`) gives the unit, skill title and description, level-based length rules, and asks for exactly 5 distinct one-sentence lines, with `translation` and `note` in the native language. Up to 2 attempts; duplicates are dropped; 3 or more usable sentences are accepted; fewer returns 502.
- `POST /sentence/evaluate` `{ sentence, transcript, confidence?, ...learner }` -> `{ score 1-5, feedback, tip, heard, similarity, spaced, words: [{ text, ok }], source: 'ai' | 'fallback' }`. `transcript` is what the **browser's speech recogniser heard**; the AI never receives audio. Flow:
  1. `matchSpeech` (`sentence.scoring.ts`) aligns target and heard words with a longest-common-subsequence and returns per-word `ok` flags plus a Dice similarity. Comparison ignores case and punctuation, ignores accents on **Latin letters only** (marks on Bengali, Hindi, Arabic are real vowels and are kept), and compares character by character for Chinese and Japanese (`spaced: false`).
  2. `anchorScore` maps similarity (blended 85/15 with the recogniser's confidence when given) to 1-5: >= 0.95 is 5, >= 0.8 is 4, >= 0.6 is 3, >= 0.35 is 2, else 1.
  3. The AI (`evaluateSystem`, temperature 0.3) returns `score`, `feedback`, `tip`; the score is clamped to within 1 point of the anchor (`clampScore`) so a weak free model cannot invent a wild rating.
  4. If the AI fails or returns unreadable JSON, the anchor score and a canned English message are returned with `source: 'fallback'`. A missing API key (503) is rethrown instead.
- `POST /sentence/complete` `{ skillId, scores: 1-5 ints (1..5 of them) }` -> `{ average, passed, percent, progress }`. Average is rounded to 1 decimal; `PASS_SCORE = 3` (exported from `sentence.service.ts`). Upserts `SentenceProgress` (keeps the best score, counts attempts, once `passed` stays `passed`) and calls `ProgressService.practice("Sentence Mode: <skill> (<avg>/5)")`, so each finished session gives +10 XP and a line in the daily feedback input.
- Sentence generation costs 1 AI request and each pronunciation check 1 more, so one session is roughly 6-12 requests of the free quota.

### Word Mode (`src/word`)
All routes are behind `AuthGuard`. Nothing here checks `premium` (see gotcha 1).

- **Catalog** (`word.catalog.ts`): `WORD_UNITS` = 10 units x 12 words (`TOTAL_WORDS` = 120). Each entry is an **English concept** with an emoji and a photo search term (`photo` defaults to the English word without a leading "to"). The AI turns the concept into the word in the learner's language, so one list serves every language. Word ids are URL slugs (`friend`, `to-laugh`, `train-station`) and the keys stored in `WordProgress`; never rename one with progress on it. Unit titles are only prompt context; the UI shows "Unit N".
- `GET /word/units` -> `{ language, percent, passed, total, units: [{ number, title, words: [{ id, emoji, passed, bestScore, inProgress }] }] }`. `language` is `Progress.language`, and only rows for that language count, so progress is **per language** (German "friend" and French "friend" are separate lessons). `inProgress` means a row exists and `finished` is false; that is what makes the frontend show the resume popup.
- `GET /word/covers?ids=a,b` -> `{ covers: { <wordId>: url | null } }` (max 12 ids, unknown ids skipped, same `WordImageService.find` photo and cache as lessons). Used by Explore for Word Mode thumbnails.
- `GET /word/unit-covers?titles=a|b` -> `{ covers: { <title>: url | null } }` (titles separated by `|`, deduplicated, at most 12; one stock photo per Learn unit title, cached as `unit-cover:<title>`). Used by `LearnView`.
- `POST /word/start` `{ wordId, targetLanguage?, nativeLanguage?, level?, restart? }` -> `{ wordId, emoji, word, translation, sentences: [{ sentence, translation, note, chunks: [{ text, meaning, explanation }] }], step, scores, resumed, image }`.
  - If an unfinished row with a valid saved lesson exists and `restart` is not true, it returns that saved lesson at the saved `step`/`scores` with `resumed: true` and **no AI call**.
  - Otherwise it asks the AI (one request, `lessonSystem`, temperature 0.7, up to 2 attempts, 2 or 3 sentences accepted, fewer returns 502), fetches the photo in parallel, upserts the row (`step 0`, `scores []`, `finished false`) and returns `resumed: false`. A finished row is treated like no row, so opening a finished word makes a fresh lesson while keeping `passed` and `bestScore`.
  - The prompt asks for `word` (with the article for languages that have one; verbs in the infinitive), its `translation` in the native language, and 3 sentences, each with `translation`, `note` and 2-3 `chunks` for the "Explain" popup. Output is validated and trimmed (`parseLesson`); chunks are optional.
- `PATCH /word/lesson` `{ wordId, language, step 0-5, scores }` saves the position after every move. Scores are cleaned by `cleanScores` (integers 1-5 or `null`, at most the number of sentences). It is ignored if the row is missing or finished. Errors on the client are swallowed, so a failed save only loses the latest step.
- `POST /word/complete` `{ wordId, language, scores }` -> `{ average, passed, percent, progress }`. Average of the non-null scores rounded to 1 decimal; `passed` needs at least one score and `average >= PASS_SCORE` (imported from `sentence.service.ts`). Upserts the row (`finished true`, `step` = sentence count, best score kept, `passed` once true stays true, `attempts` + 1) and calls `ProgressService.practice("Word Mode: <english> (<avg>/5)")` for +10 XP. If every sentence was skipped the run is closed but nothing is scored or rewarded.
- **Pronunciation is not duplicated**: the lesson page calls the existing `POST /sentence/evaluate` (same word-match + AI rating flow, same 40/min throttle).
- **Photos** (`word.images.ts`, `WordImageService`): tries Pixabay first (`PIXABAY_API_KEY`: search `hits[0]`, download `webformatURL` to `media/pixabay`, query -> picture index in `media/pixabay/index.json`, served from `/media/` by `main.ts`), then Pexels. The Pexels path: when `PEXELS_API_KEY` is set, `GET https://api.pexels.com/v1/search?query=<photo>&per_page=1&orientation=landscape` with the key in `Authorization`; uses `src.large`, `photographer` and the photo `url` for the credit. Cached in memory for the life of the process; failures (non-2xx, timeout after 6 s) are not cached and return `null`, so the UI falls back to the emoji. The in-memory cache is keyed by the caller's key **and remembers the search text**: a changed search text (an edit in the Admin panel) is a miss, so the new picture is looked up instead of serving the old one.
- Cost: a new lesson is 1 AI request, each pronunciation attempt 1 more, a resume 0.

### Flashcards Mode (`src/flashcard`)
All routes are behind `AuthGuard`. Nothing here checks `premium` (see gotcha 1). `FlashcardModule` imports `AiModule`, `ProgressModule` and `WordModule` (which exports `WordImageService` for the photos).

- **Catalog** (`flashcard.catalog.ts`): `FLASH_TOPICS` = 18 topics (People, Colors, Family, Basic actions, Day and night, Drinks, Food, Animals, Numbers, Clothes, Body, Weather, Places, Transport, Home, Feelings, Jobs, School), `CARDS_PER_DECK` = 15. Each topic has `id` (URL slug, also the key stored in `FlashcardDeck`), `title`, `emoji`, `photo` (search text for the topic's cover) and `hint` (prompt context). Never rename an id that users have a deck for. Like Word Mode, the topics are language-neutral: the AI writes the words in the learner's language.
- **Decks are per user, topic and language** (`FlashcardDeck`). A deck is written once by the AI, with a photo per card, and then **saved**, so the same words come back and the marks stay attached to them.
- `GET /flashcards/topics` -> `{ language, reviewCount, topics: [{ id, title, emoji, total, known, completed, cover }] }`. `language` is `Progress.language`, and only decks in that language count. `total` is the saved card count (15 when there is no deck yet), `known` counts cards with status `known`, `completed` = a deck exists and every card is known, `cover` is a Pexels photo URL or null. `reviewCount` = cards marked learning or flagged across all decks, capped at 15. One request looks up 18 cover photos in parallel (in-memory cached, key `flash-cover:<id>`).
- `POST /flashcards/deck` `{ topicId, restart?, targetLanguage?, nativeLanguage?, level? }` -> `{ topicId, title, emoji, cards: [{ topicId, index, term, translation, example, exampleTranslation, image, status, flagged }] }`. 404 for an unknown topic.
  - A saved deck is returned with no AI call unless `restart` is true (the "New words" button).
  - Otherwise `generate()` asks the AI for the cards: up to 3 attempts (temperature 0.6, 2600 max tokens); later attempts only ask for what is still missing (plus 2 spare) and pass the terms already collected as an exclude list; duplicates are dropped case-insensitively; cards without a term or a translation are dropped. **Fewer than `MIN_CARDS` (10) usable cards returns 502** "unreadable deck"; 10 to 14 is accepted, so a deck can be shorter than 15.
  - It then fetches a Pexels photo per card in parallel (`image` is `{ url, credit, creditUrl }` or null; cached under `flash:<photo text>`), and upserts the row with every status `new` and every flag false. **Restarting resets the marks for that topic.**
  - Prompt (`deckSystem` in `flashcard.prompts.ts`): `term` is the dictionary form with its article for languages that use one (verbs in the infinitive), `translation` is 1-3 words in the native language, `example` is ONE sentence that uses the word (no numbering, quotes, emojis, romanization or brackets), `exampleTranslation`, and `photo` (2-4 English words for a concrete stock photo). Example length and word difficulty follow the level (`LENGTH`). Schema: `{ cards: [{ term, translation, example, exampleTranslation, photo }] }`.
- `GET /flashcards/review` -> the same shape as a deck, with `topicId: 'review'`, `title: 'Daily review'`, plus `language`. It collects every card marked `learning` or flagged, walking the topics in catalog order and stopping at 15 (`REVIEW_MAX`). Each card keeps its own `topicId` and `index` so marks go back to the right deck.
- `PATCH /flashcards/mark` `{ topicId, language, index (0..49), status?: 'learning' | 'known', flagged? }` -> `{ ok: true }`. Sets the card's status and/or flag. Marking a card `known` also clears its flag unless `flagged` is sent in the same call. A missing deck or an index past the end is silently ignored (still `ok`). Throttle 120 / 60 s because it fires on every click.
- `POST /flashcards/complete` `{ topicId (a topic id or "review"), known (0..50), total (1..50) }` -> `{ progress }`. Calls `ProgressService.practice("Flashcards: <title> (<known>/<total> known)")`, so a finished run gives +10 XP and a daily-feedback line. 404 for an unknown topic. `known` is clamped to `total` but otherwise trusted.
- `cleanStatus` / `cleanFlags` rebuild the per-card arrays to the deck length, so a malformed or short stored array falls back to `new` / `false`.
- `flashcard.service.ts` has its own `learner()` fallback (Spanish / English / Beginner), which differs from the AI module's (see gotcha 8).
- Cost: a new deck is 1 to 3 AI requests, opening a saved deck, marking cards and the Daily review cost 0.

The persona prompt keeps the character in voice, family-friendly and respectful with religious figures, admits to being an AI role if asked, avoids modern politics, and forbids emojis, markdown and stage directions because the reply is read aloud. ### Call Mode (`src/call`)

All routes are behind `AuthGuard` with a 40 / 60 s throttle (every spoken turn is a reply plus a review). Premium is UI-only (`CallProvider` redirects non-Premium users). `CallModule` imports `AiModule` and `ProgressModule`. Calls are now **saved** in `CallSession`: one open call per user and language plus a history of finished ones, exactly like Chat.

- **Tutor**: any of the four `TUTORS` (default `DEFAULT_TUTOR` = Kai). `tutor` is optional on start and reply so an older client still gets Kai. The tutor calls the learner by the account first name (else the first part of the email), speaks only the target language, answers in 1-4 sentences by level (`LENGTH`), never corrects mistakes (the panel does), and uses no emojis, markdown or lists because the reply is read aloud.
- **Saved calls**: `GET /call/session` -> `{ session: { id, tutor, messages, reviews, translations, seconds } | null }`; `PUT /call/session` `{ tutor, messages[1..200], reviews, translations, seconds (0..86400) }`; `POST /call/archive`; `GET /call/history` -> `{ calls: [{ id, tutor, title, count, seconds, updatedAt }] }` (50 max); `POST /call/history/:id/open`; `DELETE /call/history/:id`. `seconds` is the length of the call; reviews have no `translation` field.
- `POST /call/start` `{ tutor?, ...learner }` -> `{ teacher: { name }, opening }`. 1 AI request.
- `POST /call/reply` `{ tutor?, messages[1..30] (last must be the learner's), ...learner }` -> `{ reply }`. Calls `ProgressService.practice("Call: <message>")`, so each turn gives +10 XP and a daily-feedback line.
- `POST /call/feedback` `{ message (1-1000), ...learner }` -> `{ correct, corrected, explanation }`. Ignores capitals and punctuation because the text comes from speech recognition; a message not in the target language is `correct: false`. `explanation` is written in the native language. Retries once on unreadable JSON, then 502.
- `POST /call/translate` `{ text, ...learner }` -> `{ translation }` (the tutor's line in the native language).
- `POST /call/advanced` `{ tutor?, messages[1..30], ...learner }` -> `{ summary, strengths[1-3], mistakes[0-5] of { original, corrected, explanation }, tips[1-3] }`. 400 if the call has no learner message. Written in the native language. 1 AI request (retries once on bad JSON).
- Cost: greeting 1 request, each turn 2 (reply + review), translate 1, advanced feedback 1, resuming a saved call 0.

### Photo Mode (`src/photo`)

All routes are behind `AuthGuard` (default throttle 20 / 60 s; each judging is one OpenRouter vision request). Nothing here checks `premium` server-side. `PhotoModule` imports `AiModule` and `ProgressModule`.

- **Catalog** (`photo.catalog.ts`): `PHOTO_UNITS` = 2 units x 8 photos (`TOTAL_PHOTOS` = 16). Photo ids are `photo-<n>` (the keys stored in `PhotoProgress`) and each points at `/photo/<n>.jpg`, a file the **frontend** serves from `frontend/public/photo/`. Unit 1 = 1-8, Unit 2 = 9-16. A non-jpg file needs `photo(n, 'png')`. The backend never reads the image files.
- `GET /photo/units` -> `{ language, percent, passed, total, units: [{ number, photos: [{ id, image, passed, bestScore }] }] }`, progress for `Progress.language` only. `percent` = passed photos / `TOTAL_PHOTOS`.
- `POST /photo/judge` `{ photoId, image (data URL, png|jpeg|webp, max 5M chars), description (2-1000 chars), targetLanguage?, nativeLanguage?, level? }`. Because the backend cannot read the frontend's files, **the browser resizes the picture (max 800 px JPEG) and sends it along**. The AI (`judgeSystem` in `photo.prompts.ts`, multimodal message, temperature 0.4, up to 2 attempts, 502 if the JSON is unusable) returns `{ score 1-5, summary, corrections (max 3), better, betterTranslation, words (max 3) }`. The learner's text is treated as data, not instructions. `passed` = score >= `PASS_SCORE` (3, imported from `sentence.service.ts`). The row is upserted (best score, last score, attempts, sticky `passed`), `ProgressService.practice()` gives +10 XP, and the response is `{ result, passed, bestScore, percent, progress }`.
- Like `/ai/photo`, this needs a vision-capable model: if `openrouter/free` does not route to one, pin it with `OPENROUTER_MODEL`.
- **Result screen (frontend, `app/photo/[photoId]/page.tsx`)**: after judging, the page switches to a split view (`md:grid-cols-2`, stacked on phones). Left card "Your input" = the picture plus the learner's own description (kept in the `judged` state as `description`); right card "AI output" = score, summary, corrections, better version and new words. Before judging, and after "Try again", it is the single-column page again.

### Content (`src/content`)

All the content of the eight modes (Sentence, Word, Flashcards, Dialogue, Debate, Characters, Roleplay, Photo) lives in **one database table, `ContentItem`**: the built-in elements and the ones added in the Admin panel are the same kind of row, and **there is no content in the code**. The catalog files (`src/<mode>/<mode>.catalog.ts`, `explore/photo-queries.ts`) hold only the types, the lookups (`findSkill`, `findWord`, ...) and the **LIVE arrays** the mode services read on every request (`SENTENCE_UNITS`, `WORD_UNITS`, `FLASH_TOPICS`, `DIALOGUE_TOPICS`, `DEBATE_TOPICS`, `CHARACTERS`, `ROLEPLAY_SCENARIOS`, `PHOTO_UNITS`, `SENTENCE_PHOTO`). They start **empty** and `ContentStore` fills them from the database. No mode service had to change.

- **Where the built-in content came from**: the migration `20261108150000_content_builtin_data` inserts the 283 built-in elements (`seeded = true`, `position` = catalog order, `data` and `original` = the element, with `unit` and `unitTitle` for Sentence/Word and `url` for Photo). It never changes a row that already exists. Every environment (dev, a fresh `migrate reset`, production) gets the content from `npm run prisma:deploy`; nothing is inserted at runtime.
- **`ContentStore`** (`content.store.ts`, global `ContentModule`, loaded first in `AppModule`): `onModuleInit` reads every row, sorts it (unit number first for Sentence/Word/Photo, then `position`, then age) and calls `DEFS[mode].load(...)` with the rows that are not deleted, which replaces the live array **in place** (`splice`, so every importer keeps the same array). It then starts a **poll** (every 15 s one `aggregate` query: row count + latest `updatedAt`); a change made by another API instance triggers a full reload, so several servers show the same content. Our own writes reload their mode at once. If the table cannot be read the API **does not start** (error logged with the fix): serving empty content would be worse, and a platform restart heals a short outage. An empty table logs a warning.
- **`content.defs.ts`**: one definition per mode (`DEFS`): `normalize` (validates a raw payload, builds the id from the title with `slug()`), `load` (stored data -> the live array; Sentence/Word/Photo group by `data.unit`, and a unit's title is the first `data.unitTitle` found among its elements, so every built-in element carries its unit's title), `rowOf` (the admin table line). Also `unitsOf`, `nextPhotoId(ids)`, `MODES`, `MODE_LABEL`, validators.
- **Stored data** (`ContentItem.data`): what `normalize` returns (same fields as the admin form, lists as arrays). Built-in Photo rows hold `url` (a path in the FRONTEND's `public/photo`) instead of `file`; uploaded pictures hold `file` (under `<MEDIA_DIR>/admin-photos/`) and the data URL in `image`, which `ContentStore.ensureFile` uses to re-create a missing file on every load.
- **Row flags**: `seeded` = a built-in element; `edited` = a built-in element an admin changed; `deleted` = hidden from learners; `original` = the built-in element exactly as first loaded (null for added ones). **Delete** removes the row of an added element for good, but only sets `deleted = true` (and puts `original` back as `data`) on a built-in one. **Reset** (after an edit) and **Restore** (after a delete) copy `original` back into `data`, clear the flags and discard an uploaded replacement picture; they need no code. A built-in row without an `original` cannot be reset (400). Learners' progress rows are never touched.
- **To change content** (built-in or not) use the Admin panel, or update the row (SQL / a data migration). To ship new built-in elements to every environment write a **data migration** that inserts rows with `seeded = true`, `original = data` and the next `position` (see `20261108150000_content_builtin_data` for the shape).
- Fixed course paths in the frontend still list built-in ids: `GET /content/course-items` returns `removed` (deleted built-in words, sentences, dialogues) so `LearnView` hides them.


### Admin (`src/admin`)

The Admin panel's API. It validates what the panel sends, keeps pictures and does the CRUD on top of `ContentStore` (see "Content (`src/content`)"); the mode services do not know about it.

- **Who is an admin**: `ADMIN_EMAILS` (see Environment variables). `AdminGuard` repeats `AuthGuard`'s token check and then requires the token's email to be in that list (403 otherwise). `GET /admin/me` only needs a login and answers `{ admin, configured }`; the Account menu uses it to show the "Admin panel" row. Throttle 120 / 60 s.
- `GET /admin/overview` -> `{ modes: [{ mode, label, total, custom, units: [{ number, title }] | null }], roleplayCategories, characterKinds }` (`units` only for sentence, word, photo, and feeds the Unit picker). `GET /admin/items?mode=` -> `{ mode, rows: [{ id, title, sub, emoji, group, custom, image?, status? }] }`: the compact table, built-in and custom together, in catalog order; `status` is `edited` or `deleted` for built-in elements an admin changed (deleted ones are listed at the end so they can be restored). Every count answer (`overview`, create, update, delete, restore, import) carries `changed` = built-in elements edited or deleted.
- `GET /admin/covers?mode=&ids=a,b` (at most 24 ids) -> `{ covers: { <id>: url | null } }`: the pictures the table shows instead of the emoji. Each mode finds its picture like the learner screens do, so the stock-photo cache is shared: an uploaded picture (`data.file`) first, then Photo = the built-in path (`data.url`), Characters = `CharacterPhotoService.cover` (the Wikipedia picture, after `ensure()`, at most 8 s), Word = `images.search(<wordId>, data.photo)`, others = `images.search('<sentence|flash|dialogue|debate|roleplay>-cover:<id>', data.photo)`. Four lookups at a time; a failed lookup is `null`, not an error; without `PIXABAY_API_KEY` / `PEXELS_API_KEY` every answer is `null` and the table keeps the emoji. `AdminModule` imports `WordModule` and `CharactersModule` (which now export `WordImageService` / `CharacterPhotoService`).
- `POST /admin/items` `{ mode, item }` adds one element; `POST /admin/import` `{ mode, items[1..200] }` adds many (each checked on its own, answer `{ created, failed, results: [{ index, ok, id?, error? }], total, custom, units }`; not for `photo`); `DELETE /admin/items/:mode/:id` deletes an element (an added one for good; a built-in one is hidden, see "Built-in elements"); `POST /admin/items/:mode/:id/restore` undoes the changes to a built-in element (Reset after an edit, Restore after a delete; 404 when it is unchanged). Bad input is a 400 with a readable message, a duplicate id a 409.
- **How an element goes live**: `AdminService.create` validates with `DEFS[mode].normalize`, saves a picture if there is one, inserts a `ContentItem` row (`seeded = false`, `position` = last + 1, `createdBy` = the admin's email) through `ContentStore.insert`, which reloads that mode's live array. Every other server picks it up within 15 s. The old `TOTAL_SKILLS`, `TOTAL_WORDS`, `TOTAL_PHOTOS` constants are the functions `totalSkills()`, `totalWords()`, `totalPhotos()` (a constant would go stale).
- **Fields per mode** (the form definition is `FORMS` in `frontend/lib/admin.ts`): Sentence `unit, unitTitle?, title, emoji, description, photo?, sentences?, course?`; Word `unit, unitTitle?, english, emoji, photo?, examples?, course?`; Flashcards `title, emoji, photo, hint, words?`; Dialogue `title, emoji, photo, partner, partnerEmoji, setting, script?, course?`; Debate `title, emoji, statement, photo`; Characters `name, emoji, kind (history|myth|fiction), hue 0-360, about, image?`; Roleplay `title, category, emoji, photo, partner, partnerEmoji, scenario, tasks[3]`; Photo `unit, image`. `unit` must be an existing unit or the next number (a new unit; Sentence and Word then need `unitTitle`). The id comes from the title (letters and digits only, so a title without any is rejected); an id that already exists in the mode, built-in or custom, is a 409. Photo ids are `photo-<n>` with n one above the largest in use.
- **Photos**: the browser shrinks the picture to a JPEG data URL (max 1200 px) and sends it; the API checks the type and size (under 3 MB), saves the file to `<MEDIA_DIR>/admin-photos/photo-<n>.<ext>` and serves it at `<PUBLIC_API_URL>/media/admin-photos/...`. The data URL is also kept in `ContentItem.data.image`, and `ContentStore` re-creates a missing file from it on every load, so photos survive a redeploy even without a volume. Deleting an added photo removes the file and the row. A built-in photo keeps its own picture (`data.url`) unless a new one is uploaded.
- **Deleting** (see "Content (`src/content`)" for added vs built-in elements) never touches learners' progress rows; the services already ignore ids that are not in the catalog (`findSkill` / `findWord` / `findPhoto` checks), so they are simply not counted. A deleted id can never be reused by a new element (409; `nextPhotoId` also counts deleted photo rows), because progress rows still carry it. A unit that loses its last element disappears; a unit's title lives on its elements (`unitTitle`).
- **Editing** (`GET /admin/items/:mode/:id`, `PATCH /admin/items/:mode/:id` `{ item }`): any element, built-in or added, can be changed in place. Its **id never changes** (it is the web address and the key of learners' progress rows, so progress keeps counting). The row in `ContentItem` is updated (a built-in one also gets `edited = true`) and the mode is reloaded. A unit title is kept. A deleted element must be restored first (400). `course` stays empty for built-in elements (they are already on their courses' paths; the form hides the field). `GET` returns the stored data shaped for the form (lists as one line per entry, a script as `Partner:`/`You:` lines, `imageUrl` for a picture).
- **Learner-facing text is now optional per element**, written in **English** and translated by the AI into each learner's language (one list still serves every language, so the text cannot be stored in the target language). Fields: Sentence `sentences` (3 to 5 lines; the AI translates them instead of inventing 5; `SentenceSkill.sentences`, `sessionSystem` uses `fromSource`); Word `examples` (1 to 3 lines; the first N of the 3 lesson sentences are translations of them, the AI writes the rest; `WordItem.examples`); Flashcards `words` (5 to 15 lines; the deck is exactly these words, `deckSize(topic)` replaces the constant 15 for the topic grid total, `FlashcardService.generateFixed` asks for the whole list each attempt and keeps the best answer); Dialogue `script` (3 to 5 turns as `Partner:` / `You:` lines; `fromScript` prompt). Empty means the old behaviour (the AI writes it from the title and hints). The dialogue script cache key includes `DialogueTopic.rev` (a hash of the stored data), so an edit is not served from the old cache. **Already saved per-user results are not rewritten**: Word lessons in `WordProgress.lesson` and Flashcards decks in `FlashcardDeck.cards` keep their old text until the learner restarts them. Debate, Roleplay and Characters are live AI chats, so there is no fixed text to supply (their scenario, tasks and persona are already admin-written).
- **Course paths**: Sentence, Word and Dialogue elements take an optional `course` (a course id from `COURSES` in `frontend/lib/courses.ts`; validated only as a slug, unknown ids are ignored by the frontend). `AdminService.courseItems()` derives them from the stored rows (not deleted, `data.course` set), and `GET /content/course-items` (`ContentController`, `AuthGuard`, any logged-in learner, 60/min) returns `{ items: [{ mode, id, title, course }], removed: [{ mode, id }] }` for the Learn tab. See "Courses and Learn".
- **Character portraits**: Characters take an optional `image` (a data URL, the browser shrinks it to 800 px; same type and size checks as photos). It is saved to `<MEDIA_DIR>/admin-photos/char-<id>-<stamp>.<ext>` (a new name on every replacement, so browsers do not keep the old picture), also kept in `ContentItem.data.image` and restored by `ContentStore.ensureFile`. `Character.portrait` holds its URL and `CharactersService.list` returns it as `cover` ahead of the Wikipedia picture. `PATCH` with a new `image` replaces it, `removeImage: true` removes it, neither keeps it.
- Cost: no AI requests. Each listing is one cheap in-memory read.

### Account (`src/account`)
All routes are behind `AuthGuard`. **Billing is not connected**: plans have no prices and nothing is charged; everything is demo logic so the Account page has something to manage.

- **Support**: `POST /account/support` `{ type, message }` (`type` must be one of `SUPPORT_TYPES` in `account.options.ts`, message up to 3000 characters, 3 a minute) stores a `SupportMessage` row with the sender's account email. **No email is sent yet**: `MailService` (`src/auth/mail.service.ts`) exists for verification and reset mails, but `sendSupport` does not use it. Read the table in the database, or wire the mailer into `AccountService.sendSupport` to forward it to support@talkmate.ai. `SupportView` shows only a Contact us row (no Help center) and the line \"Customer support: support@talkmate.ai\"; Contact us opens the \"Send us an email\" form (a custom `IssueSelect` dropdown, not a native select, with arrow-key, Escape and click-outside handling, + message, Submit disabled until both are filled).
- **Profile**: `GET /account/profile` -> `{ email, firstName, lastName, timeZone, notifications: { emailSpecialOffers, emailLearning, appSpecialOffers, appLearning }, privacy: { optOutAiTraining, optOutProfiling } }`. `PATCH /account/profile` (`firstName`, `lastName`, `timeZone` like `UTC+05:30`), `PATCH /account/notifications`, `PATCH /account/privacy` take any subset and return the full profile. `POST /account/password` `{ currentPassword, newPassword }` (bcrypt check, wrong current password is a 400 so the frontend does not log out; limited to 5 a minute). `PATCH /account/avatar` `{ image }` (a `data:image/jpeg|png|webp;base64,...` URL, max about 400 KB) and `DELETE /account/avatar` set or clear the profile picture; it is returned as `avatar` (string | null) by `GET /account/profile` **and** by the `/progress` snapshot, so the top-right account button shows it. `DELETE /account` removes the user and everything else via the cascade rules. All of these are columns on `User` (`name` is the first name, plus `lastName`, `avatar`, `timeZone` and the six booleans). The notification and privacy switches are **stored only**: no emails are sent and nothing reads the opt-outs yet. The email address is read-only. The real password reset runs from the login page (`/forgot-password`); the "Forgot password? Click here" link on the Change password sub-page still only shows a toast.
- **Personalization**: `GET /account/personalization` -> `{ values: { reason, frequency, goal, style, ageRange } (each string | null), questions: [{ key, label, options[] }] }`; `PATCH /account/personalization` takes any subset of the five keys and upserts the `Personalization` row. The question list lives only in `account.options.ts` (`QUESTIONS`): the DTO validates with `@IsIn(optionsFor(key))` and the frontend renders whatever the server returns. The answers are stored but **nothing reads them yet** (the AI prompts ignore them).
- **Refer a friend**: `GET /account/referral` -> `{ code, invited, rewarded }`. The 6-character code (alphabet without look-alikes `0 O 1 I L`) is created lazily on the first call and stored in `User.referralCode` (unique; up to 5 retries on a Prisma `P2002` collision). `invited` counts users with `referredById = you`; `rewarded` counts those whose `referralRewarded` is true. The invite link is `<origin>/login?ref=<CODE>`.
- **Reward**: when a referred user starts their first subscription, `rewardForReferral` flips the friend's `referralRewarded` with `updateMany ... where referralRewarded = false`, so a double click pays out once, then `grantFreeMonth` adds one month to **both** users' `currentPeriodEnd` (from `max(now, current end)`) and sets `premium = true`. A user with no plan gets a `canceled` 1-month plan, which does not renew. The claim and the grants are separate writes, so a failure in between loses the reward.
- **Subscriptions**: one `Subscription` row per user: `months` (plan length), `status` (`active` | `paused` | `canceled`), `currentPeriodEnd` (the end of the period already paid for). `PLAN_MONTHS = [1, 3, 12, 24]` in `subscription.util.ts` (the frontend has its own copy). Endpoints: `GET /account/subscription` and `POST /account/subscription/{plan, pause, resume, cancel}`; all return `{ status: 'none' | 'active' | 'paused' | 'canceled', months, nextPayment, accessUntil, premium }`.
  - `none` means no row, or a paused/cancelled plan whose `currentPeriodEnd` has passed.
  - Active: `nextPayment` is `currentPeriodEnd` stepped forward in whole plans until it is in the future (`nextPayment()`); `accessUntil` is null. Paused/cancelled: `accessUntil = currentPeriodEnd`, `nextPayment` null.
  - `plan` (`{ months }`, must be in `PLAN_MONTHS`) works while active or paused. `pause` needs active and moves `currentPeriodEnd` to the end of the paid period. `resume` needs paused. `cancel` works while active or paused and keeps access until the paid period ends. Wrong-state calls return 400.
- **`syncPremium`** (`subscription.util.ts`): when a subscription exists, is not `active`, and has run out, it sets `Progress.premium = false`. It runs inside `ProgressService.snapshot` and `GET /account/subscription`. **Active plans never expire** (nothing renews or charges), and a user who got Premium from the old demo unlock without a `Subscription` row is never switched off.

### Database (`prisma/schema.prisma`)
20 models. Timestamps (`createdAt`, `updatedAt`, `expiresAt`, `currentPeriodEnd`) are `DateTime`; day keys (`PracticeEntry.day`, `PracticeDay.day`, `Progress.lastDay`) are `YYYY-MM-DD` strings.

- `User(id cuid, email unique, name? (the first name), lastName?, avatar? (a small square data URL), timeZone default "UTC+00:00", passwordHash? (null for Google-only accounts), googleId? unique, emailVerified default false, emailSpecialOffers / emailLearning / appSpecialOffers / appLearning default true, optOutAiTraining / optOutProfiling default false, createdAt, referralCode? unique, referredById? -> User (onDelete SetNull), referralRewarded Boolean)`. The self-relation is named `Referrals`. `emailVerified` is true for accounts that existed before verification and for Google accounts. The notification and privacy booleans are stored only (nothing reads them).
- `EmailVerification(userId PK -> User, codeHash, expiresAt, attempts default 0, sentAt)`: at most one pending code per user; `codeHash` is `sha256(userId:code)`, the code itself is never stored.
- `PasswordResetToken(id cuid, userId -> User, tokenHash unique, expiresAt, createdAt)`, index on `userId`: `tokenHash` is the sha256 of the emailed token, the token itself is never stored.
- `Progress(userId PK -> User, xp, streak, longest, messages, lastDay "YYYY-MM-DD"?, premium, language default "Spanish", level default "Beginner", nativeLanguage default "English", updatedAt)`. (`giftClaimed` was dropped.)
- `PracticeEntry(id cuid, userId, day "YYYY-MM-DD" (UTC), text, createdAt)`, index on `(userId, day)`.
- `PracticeDay(userId, day "YYYY-MM-DD" (browser local), seconds)`, composite PK `(userId, day)`.
- `SentenceProgress(userId, skillId, bestScore Float, lastScore Float, attempts, passed, updatedAt)`, composite PK `(userId, skillId)`; `skillId` must match an id in `sentence.catalog.ts`.
- `DialogueProgress(userId, topicId, bestScore Float, lastScore Float, attempts, passed, updatedAt)`, composite PK `(userId, topicId)`; `topicId` must match an id in `dialogue.catalog.ts`. Not per language, like Sentence Mode.
- `DebateSession(userId, topicId, side, language, messages Json, reviews Json, translations Json, count, updatedAt)`, composite PK `(userId, topicId, side, language)`; `topicId` must match an id in `debate.catalog.ts`, `side` is `for` | `against`. `reviews` / `translations` are keyed by message index.
- `CharacterSession(userId, characterId, language, messages Json, reviews Json, translations Json, count, updatedAt)`, composite PK `(userId, characterId, language)`; `characterId` must match an id in `characters.catalog.ts`. `messages` is `[{ role, content }]` starting with the character's opening; `reviews` and `translations` are keyed by message index. One saved conversation per character and language.
- `RoleplaySession(userId, scenarioId, language, messages Json, reviews Json, translations Json, count, updatedAt)`, composite PK `(userId, scenarioId, language)`; `scenarioId` must match an id in `roleplay.catalog.ts`. `reviews` / `translations` are keyed by message index.
- `ChatSession(id cuid, userId, language, tutor default "Emma", messages Json, reviews Json, translations Json, count, archived default false, createdAt, updatedAt)`, index on `(userId, language, archived)`. **Many rows per user and language**: at most one is open (`archived = false`), the others are the Chat history.
- `CallSession(id cuid, userId, language, tutor default "Kai", messages Json, reviews Json, translations Json, count, seconds, archived default false, createdAt, updatedAt)`, same index and same open-plus-history idea as `ChatSession`.
- `Personalization(userId PK -> User, reason?, frequency?, goal?, style?, ageRange?)`: nullable strings holding the chosen option text.
- `Subscription(userId PK -> User, months default 1, status default "active", currentPeriodEnd DateTime, createdAt, updatedAt)`.
- `SupportMessage(id cuid, userId -> User, email (the account email when they wrote), type, message, createdAt)`, index on `createdAt`.
- `WordProgress(userId, wordId, language, lesson Json?, step, scores Json default [], finished, passed, bestScore, attempts, updatedAt)`, composite PK `(userId, wordId, language)`. `lesson` stores the generated lesson so a resume shows identical content; `finished` is the current run, `passed`/`bestScore` are lifetime.
- `FlashcardDeck(userId, topicId, language, cards Json, status Json default [], flagged Json default [], updatedAt)`, composite PK `(userId, topicId, language)`. `cards` is `[{ term, translation, example, exampleTranslation, photo, image }]`; `status` is one of `new | learning | known` per card and `flagged` a boolean per card, **both matched to the card by array index**, so never reorder or trim `cards` without rewriting both arrays. `topicId` must match an id in `flashcard.catalog.ts`.
- `PhotoProgress(userId, photoId, language, bestScore Int, lastScore Int, attempts, passed, updatedAt)`, composite PK `(userId, photoId, language)`. `photoId` must match an id in `photo.catalog.ts`; a score of 3 or more sets `passed`, which stays true.
- `ContentItem(id cuid, mode, itemId, position Int?, data Json, original Json?, seeded Boolean default false, edited Boolean default false, deleted Boolean default false, createdBy? (admin email), createdAt, updatedAt)`, unique `(mode, itemId)`, index `(mode, position)`: one row per element of the eight content modes, built-in and added together (see "Content (`src/content`)"). `mode` is one of `sentence | word | flashcards | dialogue | debate | characters | roleplay | photo`, `itemId` is the URL slug (it keys learners' progress rows and never changes), `data` is the validated element, `original` the built-in element as first loaded (what Reset puts back). Not related to `User`, so it is never cascaded. It replaced `CustomContent` and `BuiltinOverride`.
- All child relations `onDelete: Cascade` (except `referredBy`, which is `SetNull`).
- Never edit an applied migration. Change the schema, then run `npx prisma migrate dev --name <change>` and commit the generated folder.

## Frontend in detail

### Shell and routing
- `/` redirects to `/dashboard`. `/login` toggles between login and register and **clears the token on mount**, so visiting it logs you out. The register form asks for **First name** and **Last name** side by side, both required (HTML `required`, a blank-after-trim check in `submit`, and the DTO on the server). After a successful register the page switches to a **verify** step (6-digit code box, "Resend code" with a 60 s countdown, "Use a different email"); a login that answers `EMAIL_NOT_VERIFIED` opens the same step. The Google button block stays mounted but hidden during that step so it is not lost. ### `lib/api.ts`
Single API client. `BASE` = `NEXT_PUBLIC_API_URL`. Token key `talkmate-token` in `localStorage`. `request()` adds the Bearer header, turns network failure into "Can't reach the server...", flattens Nest validation message arrays, and on any 401 (when a token existed) clears it and hard-redirects to `/login`. `keepalive` is used for the final timer flush on unmount. Exports types `Msg`, `ChatMode` and `GenerateType` (both legacy), `Learner` (`targetLanguage`, `level`, optional `nativeLanguage`), `Progress` (includes `nativeLanguage` and `avatar`), `Stats`, `Achievement`, and one set of types per mode (`SentenceUnits`, `WordUnits`, `WordLesson`, `PhotoUnits`, `FlashTopics`, `FlashDeck`, `DialogueTopics`, `DebateTopics`, `DebateFeedback`, `CharacterList`, `RoleplayScenarios`, `ChatSaved`, `ChatHistoryItem`, `CallSaved`, `CallHistoryItem`, `CallAdvanced`, ...), plus the Account types `PersonalizationData`, `ProfileData`, `NotificationPrefs`, `PrivacyPrefs`, `Referral`, `SubscriptionInfo`. The `api` object has one namespace per area: `auth` (`login`, `register`, `verifyEmail`, `resendVerification`, `google`, `forgotPassword`, `resetPassword`), `progress`, `account` (everything under `/account`), `sentence`, `word` (also `covers` and `unitCovers`), `photos`, `flashcards` (`deck()` throws if `topicId` is empty), `dialogue`, `debate`, `characters`, `roleplay`, `chat`, `call`, plus `api.feedback` (daily feedback). `api.auth.register` takes `{ email, password, firstName, lastName, referralCode?, remember? }` (both names required) and returns `{ verify: true, email }`, not a token; `verifyEmail` returns the token. `request()` puts the backend's `code` field on the thrown Error (`err.code`, e.g. `EMAIL_NOT_VERIFIED`). The chat-style namespaces share one shape: `start`, `reply`, `feedback`, `translate` and either `session` / `save` / `clear` (debate, characters, roleplay) or `session` / `save` / `archive` / `history` / `open` / `remove` (chat, call; chat also has `suggestions`, call also has `advanced`).

### Sentence Mode pages (`app/sentence`)
Flow: Home -> `/sentence` -> `/sentence/<skillId>` -> `/sentence/<skillId>/practice`. All three share `SentenceProvider` via `app/sentence/layout.tsx`.

- `/sentence/<skillId>/practice` (full screen, no sidebar):
  - Loads a session from `sessionStorage` (key `talkmate-sentence:<skill>:<language>:<level>:<native>`) or calls `api.sentence.session`. The state `{ items, idx, results }` is saved on every change so a refresh keeps the same sentences, and removed when the session finishes. The native language is in the key so changing "Choose translation language" never reuses old translations.

The sentence is then coloured word by word (green matched, red missed), with stars, feedback, tip, and "We heard: ...". **Try again** clears the result; **Next/Finish** advances; **Skip** records the sentence as skipped (not scored).
  - Finishing calls `api.sentence.complete` with the scores of non-skipped sentences (nothing is saved if all were skipped) and shows a summary with Practise again / Back to units, then reloads the unit list.

  - Sending: the partner's reply and the message review run in parallel. Speech input uses the browser `SpeechRecognition` and sends what it heard when recognition ends. Speaker and Slow speech share the Sentence Mode preferences in `localStorage` `talkmate-sentence-prefs`.
  - `components/roleplay/Feedback.tsx` holds the review UI. Debate still has its own copy of the same components.

### Account page (`components/account`)
`AccountView` (props: `s`, `onSettings`, `onLogout`, `onToast`, `onSnapshot`) keeps a local `view` state (`menu` | sub-page) instead of using routes, so Account is always `/dashboard` with the Account tab active.

- **Menu**: an "Account settings" list of cards for Profile, Personalization, Settings, Subscriptions, Refer a friend, Support (an **Admin panel** row appears before Support for admins only, from `GET /admin/me`; it does `router.push("/admin")`) and Log out, plus a footer of legal titles that are plain text, not links. (The old Target language card on this menu is gone; the language now lives in Settings.)
- `SettingsView`: three picker fields, **Choose translation language** (`nativeLanguage`), **Choose target language** and **Change your target language level**, each opening a `Picker` popup (search box for languages, a card per option, Save enabled only after picking something new). Saving calls `onSettings` (the dashboard's optimistic `PATCH /progress/settings`) and shows a "Saved" toast. Flags come from `https://flagcdn.com/w80/<code>.png` (an external request) with a two-letter badge as fallback. `Picker`, `PickerField`, `LANGUAGE_OPTIONS` and `LEVEL_OPTIONS` are exported and reused by the Chat and Call Settings dialogs.

- `ReferView`: read-only invite link field with a copy button (clipboard failure shows a toast asking to copy by hand), the "invited / rewarded" counts, and a three-step explainer.
- `SubscriptionView`: shows one of three states. With no plan: a "Get Premium (demo)" button that calls `api.progress.premium()` (starting a demo plan) and reloads the subscription. With a plan: a card with plan length and the next payment or access-until date, Change plan (modal with the four lengths), Pause/Resume, Cancel (confirmation modal), and Resubscribe when cancelled. After every action, and once on mount, it re-fetches `/progress` and passes it to `onSnapshot`, because the Premium flag can change (a lapsed plan switches it off). A note says billing is not connected.
- `SubPage` is the shared back-arrow header. Toasts go through the dashboard's `setToast`.

### Courses and Learn (`components/CoursesView.tsx`, `components/LearnView.tsx`, `lib/courses.ts`)
Both are tabs inside `app/dashboard/page.tsx`, not routes. The only server call of their own is `GET /content/course-items` (elements added in the Admin panel that picked a course); no migration.

- **Data** (`lib/courses.ts`): `COURSES` is 32 entries in three groups (`level` 12 with a CEFR `badge` A1.1 to C2.2, `lifestyle` 10, `professional` 10). A `Unit` is `{ title, word, sentence, dialogue }` (each id `string | null`; built-in units have all three, units made from admin-added elements may miss one): Exercise 1 opens `/word/<word>`, Exercise 2 `/sentence/<sentence>`, Exercise 3 `/dialogue/<dialogue>`. Those ids must exist in the backend catalogs (`word.catalog.ts`, `sentence.catalog.ts`, `dialogue.catalog.ts`); the lists `WORDS`, `SENTENCES`, `DIALOGUES` at the bottom of the file are copies of them.
- **Paths**: only "Absolute beginner 1" has a hand-written path (`ABSOLUTE_BEGINNER_1`, the ten units from the design). Every other course gets `pathFor(course)`: 10 units built from the existing catalogs (sentence skills and words rotate by the course's position; lifestyle and professional courses put their `dialogues` hints first and name units after the dialogue topic). Those paths are **placeholders** until real ones are written.
- **Admin-added units**: `pathFor(course, extras)` appends `extraUnits(course, extras)` after the built-in path. Elements that picked this course are grouped by kind in the order they were added: the 1st added word, sentence and dialogue form one unit, the 2nd of each the next, and a unit simply has fewer exercises when one kind runs out. The unit's title is the dialogue's, else the sentence's, else the word's. `LearnView` loads them with `api.content.courseItems()` and numbers the exercises of each unit 1..n.
- **Selected course**: `courseId` state in the dashboard, persisted in `localStorage` key `talkmate-course` (`loadCourseId`/`saveCourseId`, default `absolute-beginner-1`). Not stored on the server, so it does not follow the user to another browser.
- **Courses tab**: `CoursesView` shows the three groups as 2-column card grids (gradient tile with an emoji, title, description, badge). A card calls `openCourse(course)` in the dashboard: save the id, `setActive("learn")`, scroll to top. The selected card is not highlighted (a purple outline was removed on purpose).
- **Learn tab**: `LearnView` shows the course picker (a popover listing all courses, same `openCourse`), a percent bar and the units, each with three exercise rows. On mount it calls `api.word.units()`, `api.sentence.units()` and `api.dialogue.topics()` together (`Promise.allSettled`, so one failing mode only hides its check marks) to get the emoji, dialogue cover and `passed` flag of each exercise. It also calls `api.word.unitCovers` (`GET /word/unit-covers`, 12 titles per call) for one stock photo per unit. Percent = passed exercises / (units x 3). The book button on a unit opens a `Modal` listing its three lessons. Rows are `Link`s for Premium users; for everyone else a click calls `onLocked(mode)`, which opens the same upsell modal as a locked mode on Home.
- The exercise pages themselves are unchanged, so after finishing one the learner lands back on Home (their back links point at `/dashboard`), not on Learn.

### Explore (`components/ExploreView.tsx`, `lib/explore.ts`)
Frontend only: no endpoint, no migration. A dashboard tab (`active === "explore"`), not a route.

- **Data**: on mount it calls `api.roleplay.scenarios`, `characters.list`, `dialogue.topics`, `flashcards.topics`, `debate.topics`, `word.units`, `sentence.units` and `photos.units` together (`Promise.allSettled`, so a failing mode only hides its own card; all failing shows an error with Try again). It reloads each time the tab opens, so finished items drop out of the picks.
- **Picks**: `pickDaily(items, n, day, salt, done)` shuffles with a generator seeded by the local date (`localDay()`), then puts items the learner has not finished first. The same picks show all day and change at midnight. Nothing is stored.
- **Layout** (two columns, one below `md`): left Daily pick, Characters (carousel of 5), Dialogue (2), Photo Mode (5 thumbnails, Start now); right Roleplays (2), Word Mode (5 emoji tiles, Play now), Sentence Mode (2), Flashcards (carousel of 5), Debates (2). Titles and descriptions come from `MODES`.
- **Daily pick**: one open item from Debates, Roleplays, Dialogue or Flashcards, chosen by the date (`dailyPick`); that item is left out of its own card below.
- **Links** go to the exercise pages (`/roleplay/<id>`, `/word/<id>`, ...). Non-Premium users get the upsell modal through `onLocked`, like Learn.
- Covers are stock photos (emoji on a gradient without a Pixabay/Pexels key or when an image fails to load). Sentence lessons use `cover` from `GET /sentence/units`. Word Mode's `GET /word/units` has no photos (it would mean 120 lookups), so after choosing its 5 words Explore calls `GET /word/covers?ids=a,b,c` once and shows the photos, with the emoji tile until they arrive. Photo and Word thumbnails share one `Thumb` component: an equal square slot (`flex-1 basis-0 aspect-square`) with the picture `object-cover`, so sizes never depend on the image's own dimensions. Gradient classes live in the component, not in `lib/`.

### Admin panel (`app/admin`, `components/admin`, `lib/admin.ts`)

- `app/admin/page.tsx` (client): redirects to `/login` without a token, asks `GET /admin/me`, and shows `AdminPanel` for admins; otherwise a short message ("not an admin", or how to set `ADMIN_EMAILS` when none is configured).
- `AdminPanel`: pill tabs for the eight modes with the element count and a green `+N` for added ones and an amber `~N` for edited or deleted built-in ones; a toolbar with search, a group filter (unit, category, kind...), "Added by admin" and "Edited / deleted" checkboxes, **Import JSON** (hidden for Photo) and **Add new**; and a compact list (one 32 px line per element: emoji or thumbnail, title, details on `md`+, group chip, a Built-in / Added / Edited badge with an edit pencil, a reset arrow on edited built-in rows and a delete button; a deleted built-in row is dimmed and struck through with a Restore button). **Pictures**: each row shows its picture (`Thumb`), with the emoji until it is known and when there is none. Rows with an uploaded or built-in picture (`Row.image`, Photo and uploaded portraits) show it at once; for the others `Thumb` asks the table to look the picture up only when the row scrolls into view (`IntersectionObserver`, 300 px margin): ids are collected for 150 ms and sent as `GET /admin/covers` in batches of 20, one request at a time, so a long list does not use the stock-photo quota at once. The pictures are forgotten whenever the list reloads (an edit may have changed the search words). It shows 100 rows at a time ("Show more"). Delete and Reset ask `window.confirm`, then reload the mode. The edit form for a built-in element hides "Add to a course".
- `AddElementModal`: the form is generated from `FORMS[mode]` in `lib/admin.ts` (field kinds: text, emoji, textarea, unit, select, hue, tasks, image, portrait; the optional "own text" fields are textareas with `tall`, and `course` is a select fed by `COURSE_OPTIONS`). The Unit select lists the existing units plus "+ New unit (N)" (Sentence and Word then ask for the unit title). **Add** closes, **Add and next** keeps unit/category/kind and clears the rest. Photo mode takes several pictures at once, shrinks each in the browser (`fileToDataUrl`, max 1200 px JPEG) and uploads them one by one.
- **Edit**: every added row has a pencil button that opens `AddElementModal` with `edit={row}`: it loads `GET /admin/items/:mode/:id`, fills the form, and saves with `PATCH` (no "Add and next"; a Photo's or character's current picture is shown and replaced only if a new one is chosen). The title can be changed, the web address cannot.
- `ImportModal`: paste JSON (a list, or `{ items: [...] }`) or pick a `.json` file; "Insert example" fills `TEMPLATES[mode]`. The result lists the items that were skipped and why.
- Counts in the tabs are patched from each answer (`total`, `custom`, `units`), so no extra request is needed after an add. `lib/admin.ts` has its own small `call()` (the shared `request` in `lib/api.ts` is not exported) and does not log you out on a 403.
- `lib/photo.ts` `imageToDataUrl` now sets `crossOrigin = "anonymous"` so Photo Mode can shrink a picture served by the API (see gotcha 62).

## Recipes

**Add a chat-style mode** (conversation with a reviewing side panel): copy a sibling module rather than touching `/ai/chat`. Backend: a new `src/<mode>/` with catalog (if it has a grid), prompts, dto, service, controller and module, registered in `app.module.ts`; add a Prisma model for saved chats (and a migration); use `ProgressService.practice()` in `reply` for the +10 XP. Frontend: add the id to `ModeId` and `MODES` in `lib/modes.ts` and to the `router.push` list in `clickMode`; add `app/<mode>/` pages, a `<Mode>Provider`, and an `api.<mode>` namespace in `lib/api.ts`. Debate (grid + sides) and Roleplays (grid + scenarios) are the closest templates; Chat and Call are the templates for one-conversation-plus-history modes.

**Add a Debate topic**: use the Admin panel (Debate, "Add"): new id from the title, never rename one with saved debates; `photo` is the cover search text. (To ship it to every environment as built-in content, add a data migration, see "Content (`src/content`)".)

**Add content without code**: use the Admin panel (`/admin`, add your email to `ADMIN_EMAILS`). It covers new Sentence skills, Word words, Flashcards topics, Dialogue topics, Debate topics, Characters, Roleplay scenarios and Photo pictures, and stores them in `ContentItem`. **Content lives in the database, not in the code**: every recipe below that is about content (skills, words, topics, scenarios, photos) is done in the Admin panel; the catalog files contain no content. **Add a new content mode to the Admin panel**: a LIVE array and its types in the mode's catalog file, a definition in `DEFS` in `backend/src/content/content.defs.ts` (`normalize`, `load`, `rowOf`) and in `MODES` / `MODE_LABEL`, a form in `FORMS` (and `TEMPLATES`) in `frontend/lib/admin.ts`, and a data migration for any built-in rows; the service must read the live array on every request.

**Add a Chat/Call tutor**: add the name to `TUTORS` in `backend/src/chat/chat.dto.ts`, a persona line to `PERSONA` in `chat.prompts.ts`, the same entry (with a picture in `frontend/public/tutors/`) to `TUTORS` in `frontend/lib/chat.ts`. Saved chats keep the tutor name as plain text.

**Add a generate type** (legacy path, Home no longer opens these): `GENERATE_TYPES` in `dto.ts`, a `case` in `generateSystem`, `GenerateType` and `DEFAULT_TOPIC` in the frontend, a render block in `GeneratePanel`, a `MODES` entry, and the dashboard id array.

**Add an achievement**: append to `ACHIEVEMENTS` in `progress.service.ts` (add new facts to the `Facts` type and `stats()` if needed) and add an icon to `ICONS` in `ProgressView.tsx`.

**Change XP, level size or the study threshold**: `XP_PER_LEVEL` lives in `progress.service.ts`, `dashboard/page.tsx` and `ProgressView.tsx`; `STUDY_SECONDS` lives in `progress.service.ts` and `ProgressView.tsx`. Change all copies.

**Add or change a Sentence Mode skill**: Admin panel (Sentence). Add new skills with new ids; renaming or deleting an id orphans users' `SentenceProgress` rows and drops them from the percentage.

**Add or change a Flashcards topic**: Admin panel (Flashcards). Use `photo` for the cover search and `hint` to steer the AI. Add new topics with new ids (never `review`); renaming or removing an id orphans `FlashcardDeck` rows.

**Add Photo Mode photos or a unit**: Admin panel (Photo): upload the picture and pick the unit (8 per unit keeps 2 rows of 4; the next number after the last unit starts a new one). The built-in photos `1.jpg` to `16.jpg` stay in `frontend/public/photo/` (their rows hold `url`). Never renumber a photo that has progress.

**Add or change a Roleplay scenario**: Admin panel (Roleplay). Keep exactly three tasks, pick a `category` from `ROLEPLAY_CATEGORIES` (a new category needs the frontend `RoleplayCategory` type too, and the constant in `roleplay.catalog.ts`). Never rename an id with saved chats.

**Add or change a Word Mode word**: Admin panel (Word). Keep 12 per unit for the grid (the UI draws whatever the server sends in 6 columns). Add new words with new ids; renaming or removing an id orphans `WordProgress` rows. Use "Photo search words" to improve the photo.

**Change the Sentence Mode pass mark or scoring**: `PASS_SCORE` is in `sentence.service.ts` (Word Mode imports it from there) **and** `frontend/lib/sentence.ts`; the similarity-to-score thresholds are in `anchorScore` (`sentence.scoring.ts`); prompts are in `sentence.prompts.ts`.

**Add a Personalization question**: add an entry to `QUESTIONS` in `backend/src/account/account.options.ts`, add its key to `PersonalizationDto` (`account.dto.ts`) and to the `Personalization` model, then run a migration. The frontend renders it automatically. Nothing uses the answers until you wire them into prompts.

**Change plan lengths**: `PLAN_MONTHS` in `backend/src/account/subscription.util.ts` and `PLANS` in `SubscriptionView.tsx`.

**Add or change a course path**: add a `lvl(...)`/`life(...)`/`pro(...)` entry to `COURSES` in `frontend/lib/courses.ts` (new ids only; the id is what `talkmate-course` stores), and give it a `units` array of `u(title, wordId, sentenceSkillId, dialogueTopicId)` to replace the generated path. Check every id against the backend catalogs; a wrong id opens a broken exercise page. New catalog content is added with the existing Word/Sentence/Dialogue recipes, then referenced here.

**Add an API field**: DTO (validators) -> service -> `lib/api.ts` types/helpers -> callers. Remember `whitelist: true` drops undeclared fields.

## Known issues and gotchas

1. **Premium is only enforced in the UI.** Backend `/ai/*`, `/sentence/*`, `/word/*` and `/flashcards/*` routes never check `premium`, and `/progress/premium` unlocks any logged-in user (it now also starts a demo subscription). Needs real billing and server-side gating before launch. The frontend leaves only Chat free: `ChatProvider` has no Premium gate, while the other nine providers redirect non-Premium users to `/dashboard`.
2. **Two day systems.** `PracticeEntry.day` and the streak-lapse check use UTC; `PracticeDay.day`, streak increments and the calendar use the browser's local date. Do not mix them; the +/-1 day tolerance in `addTime` exists because of this.
3. **Streak depends on timer seconds, not messages.** Sending messages gives XP but never extends the streak; 180 s of visible-tab time inside an open mode does.
4. **XP farming**: every Regenerate and every message gives +10 XP with no limit other than the 20 req/min throttle.
5. **`addTime` is not atomic** (read, upsert, update in separate calls); concurrent requests could double or skip a streak step.
6. **README is stale**: it lists three tables (there are 19), says `cp .env.example .env` (no such file exists, nor `.env.local.example`), suggests `migrate dev --name init` although 23 migrations exist, still says `/ai/chat` serves Chat, Call and Characters, and omits most routes (`/chat`, `/call`, `/debate`, `/account`, `/sentence`, `/word`, ...). This file is the reliable source.
7. **Native language** is stored in `Progress.nativeLanguage` (default English), set with "Choose translation language" in Account > Settings (also in the Chat and Call Settings dialogs), and sent with every AI call. Translations, tips and feedback are written in it. Nothing stops it being the same as the target language.
8. **Language default mismatch**: DB default is Spanish, `ai.service.ts` fallback is Bengali (the frontend always sends the language, so this rarely shows).
9. **Duplicated types/constants** between `ai/dto.ts` and `lib/api.ts` (modes, generate types) and between backend and frontend for XP/streak constants. There is no shared package.
10. **JWT in localStorage** (README says to move to an httpOnly cookie before production). `/login` wipes the token.
11. **Loose typing**: controllers use `@Req() req: any`, AI JSON is `any`, backend `noImplicitAny` is off. Match existing style unless deliberately tightening.
12. **Free-model flakiness**: surface errors to users (the panels already show `ErrorText`); do not swallow them. Large `count` values for generate may produce truncated JSON at 1400 max tokens, which is handled by the retry then a 502.
13. **Mobile**: the dashboard now has a bottom tab bar below `md`, so the old "no mobile navigation" problem is fixed. `SentenceShell`'s sidebar (Sentence, Word, Flashcards, Dialogue, Debate, Characters, Roleplay and Photo grids) is still hidden below `md`; those pages rely on their back link.
14. Call Mode needs speech recognition (Chrome or Edge) and has **no typed fallback**: other browsers show "Speech recognition isn't supported in this browser". Replies are read with the browser's installed voices (a warning shows when none exists for the language). Calls are now saved (`CallSession`), but Premium is UI-only.
15. **Sentence Mode trusts the browser.** `POST /sentence/complete` accepts whatever scores the client sends, so a user can fake a pass. Premium is not checked on `/sentence/*` either (extends gotcha 1).
16. **Pronunciation is judged on browser speech-to-text, not on audio.** Recognition quality varies by browser and language (Bengali is weaker in Chrome's recogniser), so a correctly spoken word can be marked wrong. Replay uses the browser's installed voices: Chrome has no Bengali voice (the page shows a warning); Edge ships natural online voices. An audio-capable model or server-side text-to-speech would fix this but was deliberately not added.
17. **Free-quota burn.** A Sentence session costs roughly 6-12 OpenRouter requests, so the 50/day free cap can run out after a few sessions (see Environment variables). Starting a skill always generates new sentences; nothing is cached server-side.
18. **`PASS_SCORE` is duplicated** in `sentence.service.ts` and `frontend/lib/sentence.ts` (the backend Word Mode shares the first).
19. **Legacy `sentence`, `word` and `flashcards` generate types**: still supported by `/ai/generate` and `GeneratePanel` (its flashcards schema is `{ front, back, hint }`, unrelated to the Flashcards Mode cards), but Home no longer opens them.
20. **Unnamed migration folders**: `20261015073124_` (the nativeLanguage column) and `20261017110133_` (the Account tables). Applied migrations must not be renamed.
21. **Subscriptions are a demo.** No payment provider, no prices, no renewals: an active plan never expires, "next payment" is just a computed date, and the "update payment method" link only shows a toast. Real billing needs a provider, webhooks and server-side Premium checks.
22. **Old demo-unlocked Premium never expires**: `syncPremium` only acts when a `Subscription` row exists, so users unlocked before the Account page existed stay Premium and see "Premium is on from the earlier demo unlock".
23. **Referral rewards can still be farmed.** Email verification now exists (an email address must receive a code, Google accounts are pre-verified), which makes bulk fake accounts harder, but there is still no per-person limit and the plans are demos, so one person with several real mailboxes can collect free months. Fix before real money is involved.
24. **Personalization answers are collected but unused**, and the legal footer on the Account page is plain text, not links.
25. **`PLAN_MONTHS` is duplicated** in the backend (`subscription.util.ts`) and `SubscriptionView.tsx`.
26. **Word Mode trusts the browser** the same way Sentence Mode does: `/word/complete` and `/word/lesson` accept whatever scores the client sends, and `/word/*` does not check Premium on the server.
27. **Word lessons are only as good as the AI.** The word in the target language, its article and the translation come from a free model with no review, and the 120-word list is a first draft. Check Bengali and the other languages by hand.
28. **A saved lesson is not refreshed** when the learner changes "Choose translation language" or level partway through; "Start over" makes a new one. Progress is stored per target language, not per native language.
29. **Photos are optional and in memory**: without `PEXELS_API_KEY` every word shows an emoji, and the photo cache is lost on restart (one Pexels request per word per run). Pexels asks for a credit; the lesson page shows one.
30. **Word Mode copies the mic logic** into `usePronunciation`; the Sentence practice page still has its own copy. A bug fixed in one must be fixed in the other, or the Sentence page should be moved onto the hook.
31. **Flashcards trust the browser** like the other modes: `/flashcards/complete` accepts any `known` count and pays +10 XP each call (no cap beyond the throttle), `mark` is client-driven, and `/flashcards/*` does not check Premium on the server.
32. **A saved deck is never refreshed.** Changing "Choose translation language" or level does not rewrite the cards (only the target language selects a different deck); "New words" is the only way, and it wipes that topic's marks. A deck can hold 10 to 14 cards when the AI falls short, even though the code comments say 15.
33. **Daily review is capped at 15 cards and walks topics in catalog order**, so cards from topics late in the list can starve behind early ones. Cards stay in the review until marked known (a flag alone keeps them there).
34. **Flashcards photo load.** The first topic grid after a server start looks up 18 covers, and a new deck looks up up to 15 photos, all in parallel; the cache is in memory only and Pexels failures are not cached. Without `PEXELS_API_KEY` the grid and cards show gradients with emoji.
35. **Flashcard marks and the deck are tied by array index.** `status` and `flagged` are parallel arrays to `cards`; anything that reorders or edits a stored deck must rewrite all three together. `mark` silently ignores a missing deck or an out-of-range index, so a stale tab can lose a click without any error.
36. **`review` is a reserved route id** (`/flashcards/review`); it is checked before topic lookup in the page, not in the catalog, so a topic with that id would be unreachable.
37. **Free-quota cost of Flashcards**: a new deck costs 1 to 3 OpenRouter requests (opening saved decks, marking and the Daily review cost none), so "New words" spends quota just like a Sentence session.
38. **Roleplay covers are stock photos, not illustrations.** The grid in the design uses illustrated covers; Pexels photos (or an emoji on a gradient without `PEXELS_API_KEY`) stand in, and the chat avatar is a crop of the same cover. Swap `cover` for fixed illustration URLs if you have them.
39. **Roleplay tasks are display-only.** The AI is told the three tasks so it can create openings, but nothing tracks whether the learner did them; the check badge on the grid means "sent at least one message" in the current language. Saved chats are per language and are never refreshed when level or "Choose translation language" changes (Start over makes a new one).
40. **Roleplay trusts the browser and Premium is UI-only** like the other modes; each turn costs 2 OpenRouter requests (reply + review), so the free daily quota drains faster than in Chat.
41. **Odd migration history.** `DebateSession` and `RoleplaySession` were each created, dropped and recreated while the modes were reshuffled (`20261020072452_debte_mode` -> `20261020092603_dialogue_mode` -> `20261020093010_debate_mode`; `20261020101741_roleplay_mode` -> `20261020103847_character_mode` -> `20261020104307_`). They are applied in folder-name order; do not rename or reorder them.
42. **Photo pictures are in the repo** (`frontend/public/photo/1.jpg` ... `16.jpg`); if one is missing the photo page shows a "picture is missing" message and the AI call fails client-side before it starts. The picture is sent to the model as a base64 image on every judging (about 800 px), so it needs a vision-capable model (see Photo Mode). Premium is UI-only here too.
43. The old `PhotoPanel` + `POST /ai/photo` still exist but Home no longer opens them (`photo` is in the `router.push` list). The Photo table comes from `20261022071633_photo_mode`.

44. **Course paths are mostly generated.** Only "Absolute beginner 1" has hand-picked units; the other 31 courses reuse the same 120 words, 30 sentence skills and 21 dialogues in a rotation, so units repeat across courses and the titles do not always match the exercises. Course cards and exercise avatars use emoji on gradients (no illustrations).
45. **Course ids are duplicated.** `WORDS`, `SENTENCES` and `DIALOGUES` in `lib/courses.ts` copy ids from the backend catalogs. Renaming or removing a catalog id (which the catalogs already forbid) would break Learn links silently.
46. **Learn progress is borrowed.** Check marks and the percent are read from Word, Sentence and Dialogue progress, so the same exercise shows as done in every course that uses it, and Word progress is per target language. The selected course lives only in the browser's `localStorage`.
47. **Learn is UI-gated like everything else**: non-Premium users get the upsell on click, but the exercise URLs and the backend routes stay open.
48. **Learn was added without running `npm run build`** (no `node_modules` in that environment); run it, and click through Courses -> Learn -> an exercise, before relying on it. Tailwind classes written in `lib/` are not generated (its `content` globs only cover `app/` and `components/`), which is why the course gradients are in `CoursesView.tsx`.

49. **Explore was build-checked only** (`npx tsc` and `npm run build` pass); it was not clicked through in a browser.

50. **Downloaded photos live on the API's disk** (the media folder: `MEDIA_DIR`, else `RAILWAY_VOLUME_MOUNT_PATH`, else `backend/media`). Deleting the folder just re-downloads them; on hosting with a read-only or temporary disk (Railway without a volume) they are lost on redeploy. Pixabay allows 100 requests per minute and asks for results to be cached, which the index does. Saved flashcard decks keep the `/media/...` URL, so changing `PUBLIC_API_URL` later breaks old decks' pictures until the deck is renewed. The Pixabay path is confirmed working on the live server and on localhost (with a `PIXABAY_API_KEY` set).

51. **Sentence lessons get stock photos; Characters get Wikipedia pictures.** Sentence: `backend/src/explore/photo-queries.ts` (`SENTENCE_PHOTO`) feeds `cover` in `GET /sentence/units` (null without a Pixabay/Pexels key); Explore and the Sentence skill intro page (`/sentence/<skillId>`) show it; the unit list rows still use the emoji. Characters: `characters.photos.ts` (`CharacterPhotoService`, titles in `CHARACTER_WIKI`) asks the Wikipedia API (no key) for each character's lead image and downloads it once to `<media folder>/characters/<id>.jpg` (git-ignored, served at `/media/characters/<id>.jpg`); `GET /characters` returns it as `cover`. The first Characters load waits at most 8 s, the rest finish in the background, so a second load shows all of them; after a failure it retries after 10 minutes. A character whose article has no lead image keeps the emoji tile. Lead images are mostly public domain but not always, so the UI credits Wikipedia. Your own `public/characters/<id>.jpg` files still win when `NEXT_PUBLIC_CHARACTER_PORTRAITS=1`. To change a picture, put your own file at `<media folder>/characters/<id>.jpg` (it is never overwritten) or change the title in `CHARACTER_WIKI`. `CHARACTER_FILE` pins an exact Wikipedia/Commons file for a character and wins over the lead image (Frankenstein's Monster uses it). Not run against the live Wikipedia API in the build environment (no access); the response parsing is unit-tested with a fake response.

52. **Email verification needs real mail delivery.** Gmail SMTP with an App Password is the simplest mailer (personal accounts can send roughly 500 emails a day, and Google may block a login from an unusual server until you approve it). With Resend instead, its default sender (`onboarding@resend.dev`) only delivers to the account owner's own address, so verifying other people needs a verified domain and `MAIL_FROM` on it; with neither Gmail nor Resend configured the code only appears in the backend log. `nodemailer` and `@types/nodemailer` are new backend dependencies (run `npm install` in `backend/`). Users that existed before the `20261106120000_email_verification` migration were all marked verified (their addresses were never checked); remove the `UPDATE` line from that migration before applying it, or reset the flag by hand, to force them through verification. The migration and the verification code were syntax-checked only, not built or run: run `npx prisma migrate dev`, both `npm run build`s and click through sign-up, wrong code, resend and an unverified login before relying on it. Unverified accounts are never cleaned up automatically.

53. **Password rule is duplicated** in `backend/src/auth/password.rule.ts` and `frontend/lib/password.ts` (8+ characters, one lowercase, one uppercase, one digit; other characters such as symbols are still allowed, and only ASCII letters count). It is enforced only where a password is chosen (register, reset-password, change password), never at login, and existing users are not forced to change theirs. Change both files together.

54. **The static `/media/` folder must match `MEDIA_DIR`.** (The copy of the repo that the Admin panel change was made on still had the old `join(process.cwd(), 'media')` line in `main.ts`; it now imports `MEDIA_DIR`.) `word.images.ts` and `characters.photos.ts` save pictures to `MEDIA_DIR` (Railway volume path, `MEDIA_DIR`, or `./media` locally), so `main.ts` has to serve that same folder. It originally served only `join(process.cwd(), 'media')`, which made photos 404 on Railway with a volume; this was fixed (Pixabay photos confirmed working on the live server and on localhost). If photos show only an emoji/placeholder online again, check this first.
55. **Chat, Call and Debate trust the browser** like the other modes: saved reviews and translations are only shape-checked, XP comes from `/reply`, and Premium is UI-only (Chat is free by design). A Chat turn costs up to 3 OpenRouter requests (reply, review, suggestion bar), so the free daily quota drains faster; turn the suggestion bar off in Settings to save one.
56. **Tutor list is duplicated** in `backend/src/chat/chat.dto.ts` (`TUTORS`) and `frontend/lib/chat.ts`; the avatars are `frontend/public/tutors/<name>.png`. Saved chats and calls store the tutor name as text, so renaming one orphans the picture lookup (the UI falls back to Emma).
57. **Dead code**: `GeneratePanel` and the `sentence`/`word`/`dialogue`/`flashcards` generate types, `PhotoPanel`, `POST /ai/chat`, `POST /ai/photo`, `ChatMode`, the `openMode` branches in the dashboard, `public/call/kai.svg` and `public/modes/chat 1.png` are not reachable or used. Remove them together if you clean up.
58. **Chat and Call history is capped at 50 rows** per language in `GET /chat/history` and `GET /call/history`, and nothing deletes old archived rows automatically (each is a JSON blob of the whole conversation).
59. **Language flags are an external request** (`flagcdn.com`) in Account > Settings and the Chat/Call Settings dialogs; offline or blocked, a two-letter badge shows instead.
60. **The catalog arrays are live and filled from the database.** `SENTENCE_UNITS`, `WORD_UNITS`, `FLASH_TOPICS`, `DIALOGUE_TOPICS`, `DEBATE_TOPICS`, `CHARACTERS`, `ROLEPLAY_SCENARIOS`, `PHOTO_UNITS` and `SENTENCE_PHOTO` start empty and `ContentStore` replaces their contents in place at startup, after every admin write and after a change by another instance (15 s poll). Never cache a catalog's length or contents in a module-level constant (that is why the `TOTAL_*` constants became functions, and nothing may read a catalog at import time), and give a new catalog consumer the array, not a copy. Other API instances show a change within about 15 s, not instantly.
61. **Admin access is only `ADMIN_EMAILS`.** There is no admin role in the database and no way to grant it from the UI. The check uses the email in the JWT, which cannot change in this app (the email is read-only); a user who is removed from the list loses access on the next request, not when their token expires.
62. **Pictures uploaded in the Admin panel are served by the API, not the frontend.** `main.ts` therefore enables CORS before the static `/media/` handler and `imageToDataUrl` loads with `crossOrigin = "anonymous"`; if Photo Mode says "Couldn't load the photo" for an uploaded picture, check `PUBLIC_API_URL` (the stored URL is built from it when the API starts) and that `FRONTEND_URL` lists the frontend origin.
63. **Deleting an Admin-panel element does not delete progress.** `SentenceProgress`, `WordProgress`, `FlashcardDeck`, `DialogueProgress`, `DebateSession`, `CharacterSession`, `RoleplaySession` and `PhotoProgress` rows for that id stay (the table has no foreign key to the catalog); they are ignored while the id is missing and count again if the same title is added later, because the id is built from the title. The Admin panel cannot edit an element: delete it and add it again.
64. **Deleted built-in elements and `lib/courses.ts`.** The fixed course paths in `lib/courses.ts` still list built-in ids; `LearnView` hides the exercises an admin deleted using `removed` from `/content/course-items` (a unit left with no exercise disappears), but other code that links to a built-in id directly will show "doesn't exist" for it. **Custom elements are not in `lib/courses.ts`.** The Courses/Learn paths list ids from the built-in catalogs, so an added Word, Sentence skill or Dialogue topic shows in its own mode (and in Explore) but not in a course path. Add it to `COURSES` by hand if it should appear there.
65. **There is no content in the code.** Changing a catalog file never changes what learners see; edit the content in the Admin panel (or its row). A built-in element an admin deleted stays deleted (its row has `deleted = true`). New built-in content for every environment needs a data migration.
66. **The API needs the content migrations.** Without `npm run prisma:deploy` (tables `ContentItem` and its data) it **refuses to start** with a clear log line, and an empty `ContentItem` table starts with empty content and a warning. After pulling this change, run the deploy: it copies the old `CustomContent` and edited `BuiltinOverride` rows into `ContentItem`, then loads the built-in content (deleted built-in elements from the earlier step are not copied: delete them again).
